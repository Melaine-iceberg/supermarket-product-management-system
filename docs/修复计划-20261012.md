### 执行中发现的新缺陷（本轮已一并修复）

**DEF-20261012-05（高）：采购单创建/编辑接口恒返回 500**

`PurchaseSaveRequest.items` 上标注了 `@Max(value = 200)`。`@Max` 仅适用于数值类型，Hibernate Validator 对 `List` 无法解析该约束，在请求体校验阶段即抛 `UnexpectedTypeException`：

```
HV000030: No validator could be found for constraint 'jakarta.validation.constraints.Max'
validating type 'java.util.List<com.smms.purchase.dto.PurchaseSaveRequest$ItemRequest>'.
```

因此 `POST /purchase-orders` 与 `PUT /purchase-orders/{id}` **对任何请求体都返回 500**，与是否传入 null 明细无关。已改为 `@Size(max = 200)`（服务层另有 `MAX_ITEMS` 校验兜底）。已扫描全部 DTO，仅此一处用了不匹配的数值约束注解。

## 四、风险与回滚

* S4 会清空运行库业务数据（商品/单据/会员等），**不影响** 系统账号、角色、字典、参数、计量单位、会员等级。执行前 S1 的快照与 `db/backup/smms-20261009-145620.sql` 均可用于回滚。
* 重建后业务主键（商品 id、单据号）会变化，前端无需改动；若有外部系统引用旧单号，需重新对齐。
* `operation_log` 等日志表不清空，历史日志会引用已删除的业务对象，属预期行为。
