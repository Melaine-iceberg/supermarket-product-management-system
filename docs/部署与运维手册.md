## 3 一键部署（Docker Compose）

### 3.1 步骤

```bash
cd supermarket-product-management-system
docker compose up -d --build  # 1) 构建并启动三容器（首次构建约 5~15 分钟，视网络与缓存）
docker compose ps             # 2) 等待 smms-backend / smms-mysql 显示 healthy
```

无需任何配置即可启动：所有环境变量均有默认值（生产部署请先按 §3.3 在仓库根目录创建 `.env` 覆盖密码与端口，该文件已被 `.gitignore` 排除，不会入库）。

首次启动时 MySQL 数据卷为空，容器按文件名顺序自动执行 `01-schema.sql`（建库建表）与 `02-init-data.sql`（初始数据）；已有数据卷时不会重复执行。

### 3.3 配置项（.env）

所有变量均有默认值，零配置可启动；需要覆盖时在仓库根目录创建 `.env`（该文件已被 `.gitignore` 排除，不会入库）：

```bash
cat > .env <<'EOF'
SMMS_WEB_PORT=80
SMMS_SERVER_PORT=8080
SMMS_MYSQL_PORT=3306
SMMS_DB_ROOT_PASSWORD=Smms_root_2024
SMMS_DB_PASSWORD=Smms_dev_2024
SMMS_JWT_SECRET=请替换为不少于32字节的随机值
# SMMS_CORS_ORIGINS=http://192.168.1.10
# 公网隧道部署（§3.5）：可选
# SMMS_TUNNEL_TOKEN=eyJhIjoi...
EOF
```

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `SMMS_WEB_PORT` | 80 | 前端访问端口 |
| `SMMS_SERVER_PORT` | 8080 | 后端直连端口（调试用） |
| `SMMS_MYSQL_PORT` | 3306 | MySQL 映射端口 |
| `SMMS_DB_ROOT_PASSWORD` | Smms_root_2024 | root 密码（仅数据卷首次初始化生效） |
| `SMMS_DB_PASSWORD` | Smms_dev_2024 | 业务账号 smms 密码（后端连接用） |
| `SMMS_JWT_SECRET` | 示例值 | JWT 签名密钥（HMAC-SHA，长度 ≥32 字节，长度决定 HS256/384/512），生产必须更换 |
| `SMMS_CORS_ORIGINS` | http://localhost:5173 | **额外**允许的前端来源（逗号分隔）；本机 localhost/127.0.0.1 任意端口已默认放行。经局域网 IP/域名/隧道域名访问时**必须**追加，否则浏览器 POST（带 `Origin`）返回 403 Invalid CORS request（详见 §3.5）。填 `*` 表示放行**任意来源**，适合多设备/多网络/多域名免维护场景（`allowCredentials=true` 时后端会回显请求 Origin，不会输出 `Access-Control-Allow-Origin: *`） |
| `SMMS_WEB_BIND` / `SMMS_SERVER_BIND` / `SMMS_MYSQL_BIND` | 0.0.0.0 | 监听地址（分别对应前端 80、后端 8080、MySQL 3306 的宿主机绑定）；隧道/生产建议改 `127.0.0.1`，关闭绕过前置网关的直连入口 |
| `SMMS_TUNNEL_TOKEN` | 空 | Cloudflare Tunnel 凭据，设置后可用 `--profile tunnel` 启动 cloudflared（见 §3.5）；空值时该服务不会启动 |
| `SMMS_TASK_FILE_DIR` | 容器内 `/app/task-files` | 异步任务结果文件目录（Dockerfile 已设并预建）。**非持久化**：容器重建会丢失文件，任务记录仍在库中（重新下载会报 1905，重新提交即可）。若需保留，可在 compose 给 backend 增加卷映射 |
| `SMMS_TASK_RETAIN_HOURS` | 24 | 任务与结果文件保留时长（小时），到期由定时任务清理记录与文件 |
| `SMMS_TASK_CORE_POOL` / `SMMS_TASK_MAX_POOL` / `SMMS_TASK_QUEUE_CAPACITY` | 2 / 4 / 50 | 后台任务线程池核心/最大线程数与排队容量；队列满时提交返回 1904 |
| `SMMS_UPLOAD_DIR` | 容器内 `/app/uploads` | 商品图片存储目录（IR-SW-05；compose 已映射 `uploads-data` 卷持久化，容量按商品数评估） |
| `SMMS_BACKUP_DIR` / `SMMS_BACKUP_RETAIN` | `/app/backups` / 30 | 数据备份目录（`backups-data` 卷）与保留份数（FR-SYS-10，默认 30 份） |
| `SMMS_MYSQLDUMP` | `mysqldump` | 备份命令路径（后端镜像已安装 default-mysql-client；自定义镜像可覆盖） |
| `SMMS_LOG_DIR` | 容器内 `/app/logs` | 文件日志目录（logback 按天/大小滚动 + ERROR 独立文件；`backend-logs` 卷持久化） |

后端在容器内以 `SPRING_PROFILES_ACTIVE=docker` 运行，全部连接参数经上述环境变量注入（`application.yaml` 提供默认值），无需在容器内保存本地配置文件。

### 3.4 启停、日志与升级

```bash
docker compose stop                     # 停止（保留数据卷）
docker compose down                     # 停止并删除容器（保留数据卷 mysql-data）
docker compose logs -f backend          # 跟踪后端日志
docker compose logs --tail=200 mysql    # 查看数据库日志
docker compose up -d --build backend    # 后端代码更新后重建升级（前端同理）
docker compose exec mysql \
  mysql -usmms -p"$SMMS_DB_PASSWORD" smms   # 进入数据库命令行
```

> `docker compose down -v` 会**删除数据卷（清空数据库）**，仅在确认废弃数据时使用。

**仅启停后端（不动数据库与前端，日常最常用）**：

```bash
cd <仓库根目录>
docker compose restart backend        # 重启；实测约 6~10s 恢复 healthy
docker compose stop backend           # 停止（容器保留，数据卷不动；此时页面接口报 502）
docker compose start backend          # 恢复运行
docker compose up -d --build backend  # 代码或依赖变更后重建
docker compose ps                     # 确认 State 为 Up，Health 为 healthy
```

> 改过 `.env`（如 `SMMS_CORS_ORIGINS`、`SMMS_TASK_*`）后必须 `up -d backend` 重建容器才会生效，`restart` 不会重读 `.env`。
> 跨机远程运维只想临时关站：`docker compose stop backend nginx`（隧道容器可保留，不影响下次恢复）。

> **老库升级（V1.1 异步任务）**：全新部署时 `db/schema.sql` 已含 `async_task` 表；对**已有数据库**升级需先执行一次建表脚本（幂等，可重复执行）：
>
> ```bash
> docker compose exec -T mysql mysql -usmms -p"$SMMS_DB_PASSWORD" smms < db/upgrade-1.1-async-task.sql
> docker compose up -d --build backend   # 再升级后端镜像
> ```
>
> 未建表时后端启动会因缺少 `async_task` 表而健康检查失败（容器反复重启）。

> **老库升级（V1.3 批次二：权限与资金安全）**：全新部署由 `db/schema.sql`/`db/init-data.sql` 直接初始化；对**已有数据库**升级需执行一次（含 `operation_log.real_name` 新列、权限点 `sys:cat:tree` 及采购员/库管员授权；重复执行 `ALTER` 会报列已存在，可忽略）：
>
> ```bash
> docker compose exec -T mysql mysql -usmms -p"$SMMS_DB_PASSWORD" smms < db/upgrade-1.3-permission-fund-safety.sql
> docker compose up -d --build backend
> ```

> **老库升级（V1.4 批次三：报表口径与审计一致性）**：全新部署由 `db/schema.sql` 直接建表（已含新列与索引）；对**已有数据库**升级需执行一次（采购/入库/采购退货/盘点/报损/库存流水补 `business_date` 并按 `business_day_start` 回填存量、补 7 个营业日索引；重复执行 `ALTER` 会报列已存在，可忽略）。升级前建议先备份数据库：
>
> ```bash
> docker compose exec -T mysql mysqldump -usmms -p"$SMMS_DB_PASSWORD" smms > backup-before-v1.4-$(date +%F).sql
> docker compose exec -T mysql mysql -usmms -p"$SMMS_DB_PASSWORD" smms < db/upgrade-1.4-report-audit.sql
> docker compose up -d --build backend
> ```
>
> 回填口径：营业日 = 业务时刻（采购=下单、入库=入库、采购退货=创建、盘点/报损=审核（未审核取创建）、库存流水=记账）早于 `business_day_start` 则归前一日；参数默认 00:00，如已配置 06:00 脚本会按配置偏移。

> **老库升级（V1.5 批次四：功能补齐）**：全新部署由 `db/schema.sql` 直接建表（已含新表/新列）；对**已有数据库**升级需执行一次（新增 `scheduled_task_log`/`sys_backup_record` 两表、定时任务与备份菜单权限、参数 `barcode_auto_query`、`supplier_goods.last_supply_price`、`purchase_order_item.suggested_qty/suggested_price`、17 张业务表审计四字段、实收/退货单价精度 12,4；重复执行 `ALTER` 会报列已存在，可忽略）。升级前先备份数据库：
>
> ```bash
> docker compose exec -T mysql mysqldump -usmms -p"$SMMS_DB_PASSWORD" smms > backup-before-v1.5-$(date +%F).sql
> docker compose exec -T mysql mysql -usmms -p"$SMMS_DB_PASSWORD" smms < db/upgrade-1.5-feature-completion.sql
> docker compose up -d --build backend
> ```
>
> **升级顺序**：若数据库早于 V1.4（缺 `business_date`）或更早版本，请按 V1.1 → V1.3 → V1.4 → V1.5（V1.6 为幂等数据修正，可在任意时点执行）顺序依次执行升级脚本后再重建后端镜像；新版后端启动即依赖新列/新表（缺失会健康检查失败或接口 500）。

> **老库升级（V1.6 批次六：低成本高价值项收尾）**：本批次无表结构变更，仅修正 `sys_config.instant_effect` 列注释与 `token_expire_hours` 参数备注（生效方式与实现一致，GAP-P2-24）；对已有数据库执行一次（可重复执行、幂等），不重建后端也不影响运行：
>
> ```bash
> docker compose exec -T mysql mysql -usmms -p"$SMMS_DB_PASSWORD" smms < db/upgrade-1.6-quality-polish.sql
> ```

### 3.5 公网发布：Cloudflare Tunnel（可选）

适用场景：**没有公网 IP**、不方便开放入站端口（80/443），或希望在域名前免费获得 HTTPS/CDN/WAF。
隧道是**出站**连接（cloudflared 主动连 Cloudflare 边缘），因此不需要开放入站端口、不需要证书、不需要改动后端与前端代码；本方案仍使用 §3 的三容器，未替换任何组件。

> 隧道只解决“入口”，MySQL 仍在本机数据卷内；若要走纯 Cloudflare（Workers + D1）需重写后端数据层，不在本手册范围内。

#### 1) Cloudflare 侧准备

1. 域名已托管在 Cloudflare（Nameserver 已指向 Cloudflare）；
2. Zero Trust 控制台 → **Networks → Tunnels → Create a tunnel**，类型选 **Cloudflared**，命名如 `smms`；
3. 在 **Public Hostname** 添加：Subdomain（如 `smms`）+ Domain（如 `example.com`），
   Service 填 `http://nginx:80` —— `nginx` 是 compose 内的服务名，在同一容器网络内解析，**不要**填 `localhost:80`；
4. 复制安装命令中的 token（`eyJh...` 开头的长串）。

> **环境选择与一个实测过的坑**：创建隧道时的「Choose your environment / 安装连接器」只是决定面板展示哪份安装片段，无论选 Debian、Windows 还是 Docker，**生成的隧道 token 是同一个**。本方案用 compose 里的 `cloudflared` 容器跑连接器，故选 **Docker**，只复制其 `docker run ... --token eyJh...` 中 `--token` 后面那串填入 `.env`；**不要直接执行面板给的这条 `docker run`** —— 新容器会挂在默认 bridge 上，不在 compose 网络（本机实测为 `smms_default`）内，Public Hostname 中配置的 `http://nginx:80` 将无法解析，表现为隧道已连上但访问返回 502。若确需手动运行，需自行补 `--network smms_default`。

#### 2) 本机启用隧道

```bash
cat >> .env <<'EOF'
SMMS_TUNNEL_TOKEN=粘贴上一步的 token
# 必填：把公网域名加入跨域白名单（否则浏览器 POST 登录返回 403 Invalid CORS request）
SMMS_CORS_ORIGINS=https://smms.example.com
# 多设备/多网络/多域名（含局域网 IP、后续新增域名）免维护：用下面这行**替换**上一行
# SMMS_CORS_ORIGINS=*
# 关闭绕过 Cloudflare 的直连入口（推荐）
SMMS_WEB_BIND=127.0.0.1
SMMS_SERVER_BIND=127.0.0.1
SMMS_MYSQL_BIND=127.0.0.1
EOF

docker compose --profile tunnel up -d --build   # 不加 --profile tunnel 时 cloudflared 不会启动
docker compose logs -f cloudflared             # 出现 "Registered tunnel connection" 即隧道已建立
```

浏览器打开 `https://smms.example.com` 即可登录。

> **为什么必须配 `SMMS_CORS_ORIGINS`**：静态页与 `/api` 虽然同源，但浏览器对 POST 等非简单请求**即使同源也会携带 `Origin` 头**，而 `SecurityConfig` 的 CorsFilter 会对不在白名单的 Origin 直接返回 `403 Invalid CORS request`（该 403 无 `Content-Type`，Firefox 会把它误报为「XML 解析错误：语法错误」）。表现为：页面能打开、`GET /api/v1/ping` 正常，但登录提示“网络异常，请检查与服务器的连接”。变更该变量后需重启后端：`docker compose up -d backend`。

#### 3) 冒烟验证

```bash
curl -fsS https://smms.example.com/api/v1/ping
# 必须带 Origin 验证登录（浏览器行为）：
curl -sS -o /dev/null -w '%{http_code}\n' -X POST https://smms.example.com/api/v1/auth/login \
  -H 'Origin: https://smms.example.com' -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"Admin@2026"}'   # 期望 200（403 即 CORS 白名单未加该域名）
# 登录一次后核对留痕 IP 是否为公网地址（而非容器内网地址）
docker compose exec mysql mysql -usmms -p"$SMMS_DB_PASSWORD" smms \
  -e "SELECT username,ip,status,login_time FROM login_log ORDER BY id DESC LIMIT 3"
```

#### 4) 停止 / 移除隧道

```bash
docker compose --profile tunnel stop cloudflared   # 仅停隧道，站点仍可本机/局域网访问
docker compose --profile tunnel down               # 连同隧道容器一起删除（数据卷保留）
# 或从 .env 删除 SMMS_TUNNEL_TOKEN，之后 docker compose up -d 不再纳入 cloudflared
```

#### 5) 隧道模式注意事项

| 事项 | 说明 |
| --- | --- |
| 响应时长上限 | Cloudflare 代理对源站响应约 **100 秒**超时（超出返回 524）。Excel 导入/报表导出等长任务已在 V1.1 改为**异步任务**（提交 <1s 返回任务号，后台生成后下载），不再受此限制；自建反向代理仍需保留 `proxy_read_timeout 300s`（`frontend/nginx.conf` 已配） |
| 客户端真实 IP | `frontend/nginx.conf` 已按 `CF-Connecting-IP` 还原真实 IP，且仅信任容器/内网网段来源，登录与操作日志记录的是访问者公网 IP |
| 直连入口 | 使用隧道时建议三个 `SMMS_*_BIND` 均设 `127.0.0.1`（已写在上文配置块中）：此后 `8801/8802/33307` 仅监听本机回环，局域网与公网均无法直连，只能经 Cloudflare 访问；本机 `curl http://127.0.0.1:8801` 与 `docker compose exec` 运维不受影响。若需局域网直连，将其改回 `0.0.0.0` 并放行主机防火墙（如 `sudo ufw allow 8801/tcp`）后 `docker compose up -d`。修改该组变量会**重建** nginx/backend/mysql 容器（数据卷保留，中断数秒） |
| 访问控制早停 | 如需只允许特定网络访问，可在 Cloudflare Access 加策略（Zero Trust → Access → Applications），应用侧无需改动 |
| 备份与运维 | 隧道只改入口，不影响 §5.1 备份、`docker compose exec` 运维与升级流程 |
| 依赖方向 | cloudflared 只依赖 nginx 已启动（`service_started`）；后端未健康时页面可打开但接口会 502，属预期 |

## 4 本地开发部署

## 5 日常运维

### 5.1 备份与恢复

**推荐方式（批次四起）**：系统内「系统管理 → 数据备份」页面可查看备份记录并一键触发（仅超级管理员）；后端每日 23:30 自动全量备份（mysqldump），文件保留最近 **30 份**（SRS FR-SYS-10；`SMMS_BACKUP_RETAIN` 可调），备份文件位于 `backups-data` 卷（容器内 `/app/backups`）。

命令行脚本（宿主机 crontab 场景）：

```bash
# 每日 23:30 自动备份（--docker 模式，走 compose 内客户端；保留 30 份）
30 23 * * * cd /path/to/supermarket-product-management-system && tools/backup-db.sh --docker >> logs/backup.log 2>&1

# 手动执行同一脚本（本机 mysqldump 模式）
tools/backup-db.sh
```

等价手工命令（结构 + 数据，含例程/触发器；保留期 30 份为口径约定，可结合 cron + find 清理）：

```bash
# 备份
docker compose exec -T mysql \
  mysqldump -uroot -p"$SMMS_DB_ROOT_PASSWORD" --single-transaction --routines --triggers smms \
  > backup_smms_$(date +%F).sql

# 恢复（停业务写入后执行）
docker compose stop backend
docker compose exec -T mysql mysql -uroot -p"$SMMS_DB_ROOT_PASSWORD" smms < backup_smms_2026-10-06.sql
docker compose start backend
```

要点：使用 `--single-transaction`（InnoDB 一致性快照）；恢复前确认无应用写入；重大升级前额外备份；备份记录（含失败原因）可在系统内页面追溯。

### 5.2 日志

| 来源 | 查看方式 | 说明 |
| --- | --- | --- |
| 容器标准输出 | `docker compose logs` | Spring Boot 运行日志（含定时任务执行结果与耗时） |
| 应用日志文件 | `docker compose exec backend ls /app/logs`（`backend-logs` 卷） | `smms.log` 按天/100MB 滚动保留 30 天；`smms-error.log` 仅 ERROR，便于排障；关键业务日志含单据号与操作人（IR-SW-07） |
| 定时任务日志 | 界面"系统管理→定时任务" | 各任务最近执行结果/耗时/重试；失败含原因（IR-SW-06） |
| 操作日志 | 界面"系统管理→操作日志" | 业务留痕（保留 ≥1 年，只增不删） |
| 登录日志 | 界面"系统管理→登录日志" | 登录成功/失败与锁定信息 |

建议：为 Docker 配置日志轮转（`log-driver: json-file` + `max-size`），或定期归档 `docker compose logs > 归档文件`。

### 5.3 参数与字典调整

- 业务参数（折扣下限、退货阈值/有效期、积分规则、建议采购 K/N 等）在"系统管理→系统参数"在线修改，立即生效（FR-SYS-06）；
- 业务枚举（收款方式、退货原因等）在"系统管理→数据字典"维护，停用项不影响历史单据展示（FR-SYS-07）；
- 连接与密钥类仅经环境变量（`.env`）调整，修改后 `docker compose up -d` 重建容器生效。

### 5.4 安全运维建议

1. 上线前更换 `SMMS_JWT_SECRET`（≥32 字节随机值）与两个数据库密码；修改 MySQL root 密码需重建数据卷或手动 `ALTER USER`；
2. 生产环境在前置网关启用 HTTPS（并配置 `SMMS_CORS_ORIGINS` 为真实域名，或填 `*` 放行任意来源）。Nginx 已默认输出安全响应头（HSTS/X-Content-Type-Options/X-Frame-Options/Referrer-Policy，NFR-SEC-09），HSTS 在 HTTPS 下由浏览器生效；
3. JWT 有效期默认 8 小时（参数 `token_expire_hours`）；权限/密码变更即时踢出旧会话（黑名单 + 权限版本）；
4. 遵循最小权限原则分配角色；敏感操作（改价/折扣/退货/充值/盘点审核）均需店长级授权与二次确认；
5. 演示账号首次登录强制建议改密，长期不用账号应停用而非删除。

### 5.6 异步任务（导出/导入）运维

V1.1 起，报表导出、商品/操作日志/预警导出与商品/会员导入提交均为**异步任务**：提交立即返回 `taskNo`，后台线程生成 xlsx，前端轮询进度并在完成后自动下载。

| 项 | 说明 |
| --- | --- |
| 任务记录 | 表 `async_task`（状态/进度/阶段/文件名/大小/操作人/过期时间） |
| 结果文件 | 容器内 `SMMS_TASK_FILE_DIR`（默认 `/app/task-files`），**非持久化** |
| 保留期 | `SMMS_TASK_RETAIN_HOURS`（默认 24h）；每小时定时任务清理过期记录与文件 |
| 并发 | 线程池 2~4 线程、排队 50（`SMMS_TASK_*`）；队列满时提交返回 1904 |
| 重启行为 | 启动时把 `QUEUED/RUNNING` 统一置为 `FAILED`（「服务重启导致任务中断，请重新提交」） |
| 权限 | 仅提交人可查询/下载（1902）；结果过期或被清理报 1905 |

常用排查命令：

```bash
# 最近 10 个任务及状态
docker compose exec mysql mysql -usmms -p"$SMMS_DB_PASSWORD" smms \
  -e "SELECT task_no,biz_name,status,progress,phase,username,error_message,create_time,finish_time \
      FROM async_task ORDER BY id DESC LIMIT 10"
# 失败任务（含原因）
docker compose exec mysql mysql -usmms -p"$SMMS_DB_PASSWORD" smms \
  -e "SELECT task_no,biz_type,username,error_message FROM async_task WHERE status='FAILED' ORDER BY id DESC LIMIT 10"
# 后端任务日志
docker compose logs backend | grep -E "异步任务(完成|失败)"
# 结果文件占用（容器重建后目录为空）
docker compose exec backend du -sh /app/task-files
```

> 结果文件不持久化是**有意取舍**：任务记录仍在库中可审计，重下载只需重新提交（大导出在秒级完成）。若业务需要长期归档，把 `backend` 增加卷映射（如 `./data/task-files:/app/task-files`）并同步调大 `SMMS_TASK_RETAIN_HOURS` 即可。

## 6 常见问题排查（FAQ）

| 现象 | 排查与处置 |
| --- | --- |
| `docker compose up` 报端口被占用 | 修改 `.env` 中 `SMMS_WEB_PORT/SMMS_SERVER_PORT/SMMS_MYSQL_PORT` 后重试 |
| 后端启动失败：数据库连接拒绝 | 等 MySQL healthy（首次初始化需 30~60s）；确认 `.env` 密码与 `SMMS_DB_PASSWORD` 一致；改过 root 密码但数据卷已存在时需进入容器 `ALTER USER` 或重建卷 |
| 后端 healthy 但登录 401/500 | 检查 `SMMS_JWT_SECRET` 是否被修改为不一致值；重启 backend 重建令牌 |
| 页面打不开（Nginx 502） | `docker compose ps` 确认 backend 健康；`docker compose logs nginx backend` 查反代报错 |
| 前端刷新 404 | Nginx 已配置 history 回退（`try_files ... /index.html`）；若自建反代需同步配置 |
| 首次构建卡在依赖下载 | 配置 Maven/npm 镜像加速；构建层已缓存，重试即可 |
| 导入大 SQL（仿真数据）中断 | 用 `mysql --max_allowed_packet=64M` 重试；确认磁盘空间 ≥ 10GB；导入期间勿重启容器 |
| 操作日志/登录日志影响查询 | 日志表按时间索引；如需归档，先导出再按 `operate_time` 分历史窗口清理（只读表也允许运维归档） |
| 时间显示偏差 8 小时 | 检查容器 `TZ=Asia/Shanghai` 与 MySQL `--default-time-zone=+08:00`（compose 已内置） |
| AC-08 并发演示在本机失败 | 确认 MySQL 事务隔离为 READ COMMITTED（默认配置）；勿手工以 RR + MariaDB 快照隔离模式运行 |
| 登录提示“网络异常，请检查与服务器的连接”，控制台报 `403 Invalid CORS request` 或「XML 解析错误」 | 访问域名未加入 CORS 白名单：在 `.env` 设 `SMMS_CORS_ORIGINS=https://你的域名`（或 `*` 放行全部来源）后 `docker compose up -d backend`（§3.5 步骤 2） |
| 经 Cloudflare 访问出现 524 | Cloudflare 对源站响应约 100s 超时。报表导出与商品/会员导入已在 V1.1 改为异步任务，不再触发；若自建反代仍报 524，同步调大 `proxy_read_timeout`（`frontend/nginx.conf` 已为 300s）并确认未改回同步实现（§3.5） |
| 导出/导入长时间停在“排队中” | 后台线程被占满：`docker compose logs backend` 看任务日志，`SELECT status,COUNT(*) FROM async_task GROUP BY status` 看积压；可调大 `SMMS_TASK_MAX_POOL` 后 `docker compose up -d backend` |
| 下载结果报 1905「任务结果已过期或被清理」 | 结果文件超过 `SMMS_TASK_RETAIN_HOURS`（默认 24h），或 backend 容器重建导致 `/app/task-files` 丢失（§5.6）；重新提交导出即可 |
| 提交导出报 1904「当前后台任务较多」 | 任务队列（默认 50）已满；稍后重试，或调大 `SMMS_TASK_QUEUE_CAPACITY` |
| 任务显示「服务重启导致任务中断」 | backend 重启时未完成的 `QUEUED/RUNNING` 任务会被置为失败（设计如此，避免永久挂起）；重新提交即可 |
| 后端启动失败且日志报 `async_task` 表不存在 | 老库未执行 V1.1 升级脚本，见 §3.4 末的升级说明 |
| 日志中客户端 IP 是 172.x 内网地址 | 未经 Cloudflare 直连时属正常；经隧道应记录公网 IP，若仍为内网请在 `frontend/nginx.conf` 更新后 `docker compose up -d --build nginx` |
| `docker compose up -d` 未启动 cloudflared | 该服务由 profile 控制：需 `.env` 设置 `SMMS_TUNNEL_TOKEN` 后执行 `docker compose --profile tunnel up -d`（见 §3.5） |
| cloudflared 反复重启并提示 `Provided Tunnel token is not valid` | token 复制不完整或已在 Cloudflare 侧轮换；重新复制完整 token 写入 `.env`，再 `docker compose --profile tunnel up -d cloudflared` |
| 经 Cloudflare 访问返回 **530**，页面显示 `error code: 1033`（Tunnel 离线），但本机 `http://127.0.0.1:8801/` 正常 | 隧道链路断，站点本身健康。先看 `docker compose logs cloudflared`：若报 `TLS handshake with edge error: EOF`，多为**本机代理软件**（Clash/Mihomo 的 TUN + fake-ip）劫持了隧道出站域名——`dig +short region1.v2.argotunnel.com` 返回 `198.18.x.x` 即可确认。在代理配置中追加 `dns.fake-ip-filter: "+.argotunnel.com"` 与首条规则 `DOMAIN-SUFFIX,argotunnel.com,DIRECT`，重启代理后 `docker compose --profile tunnel restart cloudflared` |
| 隧道恢复的验证方法 | `dig +short region1.v2.argotunnel.com` 应返回真实边缘 IP（`198.41.192.x` / `198.41.200.x`）；`docker compose logs cloudflared` 出现 `Registered tunnel connection`（通常 4 条）；`curl -I https://<域名>/` 返回 200 而非 530。注意：**代理软件的订阅更新会覆盖上述两行配置**，届时隧道会再次离线，需重新追加 |
