## 3. P0 严重问题（10 项）

### GAP-P0-01 所有分页式 Excel 导出被静默截断为 500 行

| 项 | 内容 |
| --- | --- |
| 关联需求 | FR-RPT-08、FR-GOODS-12、FR-INV-05（导出）、IR-SW-04 |
| 现象与证据 | `backend/src/main/java/com/smms/config/MybatisPlusConfig.java:22` 全局 `setMaxLimit(500L)`；导出路径以 `export_max_rows+1`（50001）作为页大小（`GoodsExcelService.java:255-256`、`InventoryReportService.java:54-55/77-79/108-110`、`InventoryService.java:186-188` 等），MyBatis-Plus 会把超限页大小**静默截为 500**，`ReportExcelService.checkLimit()` 因结果 ≤500 永不触发。旁证：《测试报告》§9.1 自己列出的 `summary-goods 501 / turnover-goods 501` 行数（表头+500）即截断征兆 |
| 影响 | 2 万商品导出实际只有 500 行；库存/毛利/会员/商品分析等分页式导出全部受限；用户无任何提示 |
| 修复建议 | 方案 A（推荐）：为导出新增专用不分页 Mapper 语句（直接 `LIMIT #{limit}`），先 `count` 再 `checkLimit(total)`；方案 B：导出查询绕过 `PaginationInnerInterceptor`（独立 SqlSession）。**需逐导出点排查**，含 `GoodsExcelService`、`InventoryAlertExcelService`、`ReportExcelService` 的全部上游 |
| 验证 | 全量仿真库导出商品清单应得 20000 行；导出 500 行以上数据不再静默截断；超 5 万行提示缩小范围 |

### GAP-P0-02 销售月报只显示每月最后一天的数据

| 项 | 内容 |
| --- | --- |
| 关联需求 | FR-RPT-02①、BR-RPT-01、AC-16 |
| 现象与证据 | `backend/src/main/resources/mapper/rpt/ReportMapper.xml:43-64`：monthly 时 SELECT 用 `DATE_FORMAT(business_date,'%Y-%m')` 但 **GROUP BY 仍是 `business_date`**（第 62 行）；`SalesReportService.java:38-50` 按月 key 覆盖合并（`c.sales = s`），同月多天只保留最后一天。退货侧（`ReportMapper.xml:67-89`，GROUP BY `ro.business_date`）同病 |
| 影响 | 月报与月报导出的单数/销售额/毛利/净销售全部错误，合计行随之错误 |
| 修复建议 | monthly 分支 `GROUP BY DATE_FORMAT(...,'%Y-%m')`（销售与退货两条 SQL 同步），或服务层改为累加而非覆盖；补跨月单测 |
| 验证 | 造跨月数据：月报总额 = 该月各日报之和 |

### GAP-P0-03 日报/看板"退货额"按明细行数重复计算、退货单数错误

| 项 | 内容 |
| --- | --- |
| 关联需求 | FR-RPT-02、FR-RPT-01（7/30 日趋势）、BR-RPT-01 |
| 现象与证据 | `ReportMapper.xml:67-89`：`return_order LEFT JOIN return_order_item` 后 `SUM(ro.refund_amount)`（订单级字段被每个明细行重复累加，第 81 行）、`COUNT(*)` 为明细行数而非退货单数（第 83 行）。一张 3 行明细的退货单，退款额计 3 次、单数显示 3 单 |
| 影响 | 日报/月报的退货额、净销售、毛利额、毛利率；看板趋势；与"成本回冲正常"形成错配（毛利被低估） |
| 修复建议 | 退货额改为对 `return_order` 直接聚合（不 join 明细）；退货成本与行数另用 `return_order_item` 按 `return_id` 聚合子查询；`COUNT(DISTINCT ro.id)` 计退货单数 |
| 验证 | 造"一单多明细"退货：日报退货额 = Σ退货单头金额；退货单数 = 退货单张数 |

### GAP-P0-04 采购单"部分入库 → 全部退货"状态卡死

| 项 | 内容 |
| --- | --- |
| 关联需求 | FR-PUR-08、SRS 3.5.1 状态机、BR-PUR-08、AC-02 |
| 现象与证据 | `backend/src/main/java/com/smms/purchase/service/PurchaseReturnService.java:210-219`：`allMatch(returnedQty ≥ receivedQty)` 未考虑**仍未入库的剩余量**。订购 100、入库 40、退货 40 即被置 `ALL_RETURNED`；该状态既不能在 `ReceiptService.java:331-334`（仅 APPROVED/PARTIAL）继续入库，也不能由 `PurchaseOrderService` 关闭短少，也不在 `RETURNABLE_STATUSES`（`PurchaseReturnService.java:62-64`）中 → 剩余 60 永久悬空，并从"在途量"消失，导致建议采购量高估 |
