## 8. 性能抽样（AC-20）

**方法**：对全量仿真库（2 万商品 / 200 万销售单）经真实 HTTP 调用；每场景预热后连续采样，nearest-rank 法取 P50/P95；单实例部署、同机压测客户端。

| 场景 | 样本 | P50 | P95 | 上限（AC-20） | 结论 |
| --- | --- | --- | --- | --- | --- |
| 商品列表查询（分页 20 条/页） | 20 | 104.3 ms | 113.5 ms | ≤ 500 ms | 达标 |
| 销售日报（区间=业务量最高日 2025-02-16，2,445 单） | 10 | 14.2 ms | 15.3 ms | ≤ 2,000 ms | 达标 |
| 单笔结算（扫码取价 → 现金收款 → 落单扣库） | 15 | 25.9 ms | 145.4 ms | ≤ 800 ms | 达标 |

## 10. 缺陷记录与修复验证

测试期间共发现并修复 8 项缺陷（均含复现、根因与回归证据；DEF-01~04 为部署/E2E 阶段，DEF-05~08 为仿真数据一致性核验阶段）：

| 编号 | 现象 | 根因 | 修复与验证 |
| --- | --- | --- | --- |
| DEF-01 | 反代部署下浏览器登录 403（页面报“网络异常”） | `SecurityConfig` 显式 `allowedOrigins`（默认仅 5173）与反代部署端口不匹配；浏览器对同源 POST 亦携带 `Origin` 头，被 CORS 拒绝 | `allowedOriginPatterns` 放行本机任意端口，非本机来源仍须显式配置 `SMMS_CORS_ORIGINS`（compose 透传）；回归：带 Origin 登录 200、无头浏览器全路径截图成功 |
| DEF-02 | 入库单列表接口 500“系统繁忙” | `ReceiptOrderVO` 记录 13 个构造参数（含明细 List），`selectReceiptPage` 仅返回 12 列，MyBatis 构造器自动映射失败 | SQL 补 `NULL AS items` 占位列（列表不装载明细）；回归：列表返回 73 单、页面正常渲染（截图 04） |
| DEF-03 | 采购退货列表接口 500（同类） | `PurchaseReturnVO` 16 参 vs 查询 15 列 | 同上；回归：`/purchase-returns` 返回数据正常 |
| DEF-04 | Nginx 容器健康检查持续 unhealthy | `wget http://localhost/` 经 busybox 解析为 IPv6 `::1`，而 nginx 仅监听 IPv4 | HEALTHCHECK 改 `http://127.0.0.1/`；回归：`docker ps` 显示 healthy |
| DEF-05 | 销售日报/看板的销售成本与毛利对系统实际成交单失真（成本恒 0、毛利=销售额） | `SalesCheckoutService.insertOrder` 将头表 `cost_amount/profit_amount` 置 0 后无任何回填；而 `ReportMapper` 日报/看板按头表聚合，BR-RPT-01 口径要求等于 Σ明细成本 | 结算落库时按与明细同公式汇总头表（行成本四舍五入到分后求和，毛利=应收−成本）；回归：单测补头表断言、修复后经 API 真实结算 30 单头表=Σ明细、B06/B07 违规 0 |
| DEF-06 | 库存"成本金额 ≠ 数量×成本单价"（B05，18,444 行） | 生成器对非称重商品期初库存取整不彻底，毫单位小数碎片使结存真实值与显示值偏差（与 `InventoryMapper` 的 `ROUND(quantity×cost_price,2)` 口径不符） | 期初库存非称重商品取整为整件；小规模新旧对比（旧 287/300 坏 vs 新 0/300）；全量库等值归一化后 B05 归零 |
| DEF-07 | 退货明细"退款单价"失真（B10，89,824/91,503 行，如实付 118.53 元退 3 件应记 39.51 却记 0.04） | 生成器计算时把"分"除以"千单位数"（漏乘 1000），未对齐 `SalesReturnService` 的实付÷数量口径 | 统一整数分运算 `half_up(paid_c×1000, qty_milli)`；小规模对比旧 17,230/17,378 坏 → 新 0；全量库等值归一化后 B10 归零 |
| DEF-08 | 销售单件数与结算服务口径不一致（B06，259/1,999,235 单） | 生成器将"恰好整数的称重行"计 1 件，而 `SalesCheckoutService` 按整数值计（2.000 kg 记 2 件）；属生成器口径偏差 | 生成器按服务口径改正（整数量行取整值、非整数量行计 1）；40 万单小规模复现 29 例后修复转 0；全量库等值归一化后 B06 归零（真实成交单由 DEF-05 修复保证同口径） |

> 说明：DEF-02/DEF-03 属同类缺陷（分页查询映射与详情 VO 演进的参数数量失配），单元测试未覆盖该映射路径，由端到端实测发现；已在新版镜像中修复并回归。DEF-05 属系统级缺陷：此前单元测试仅断言明细行成本/毛利快照，未覆盖头表汇总路径，由仿真数据核验中的真实 API 结算暴露；已补断言并全量回归。DEF-06~08 属交付工具（生成器）缺陷，修复后对已导入全量库按后端同口径做等值修正，27 项核验最终全部归零（见 §7）。另修订文档勘误一处：JWT 算法说明由 “HS256” 更正为“HMAC-SHA，密钥长度决定 HS256/384/512”（部署默认 48 字节密钥 → HS384）。

## 11. 结论与局限

1. **结论**：全部 Must 级功能与 §7 验收条款（AC-01~AC-20）均具备自动化或实测证据并通过；交付物（容器化、部署脚本、六份文档、仿真数据）齐备。
2. **局限**：
   - 性能为单机抽样（非持续压力测试），P95 采样量较小（20/10/15），用于对照 AC-20 基线而非容量评估；
   - 并发验证聚焦库存扣减（AC-08），未做多收银台混合负载压测；
   - 前端以无头浏览器路径验证 + 人工操作截图，未建 UI 自动化回归套件；
   - FR-RPT-09（单据打印）/ FR-RPT-10（自定义报表）为已知未交付项，首页有明示提示，不在本次验收范围内。
