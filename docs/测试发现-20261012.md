实测输出（部署库 `smms`）：

| B05 | 库存成本 = 数量 × 成本单价 | 472 | 累计偏差 7,966.35 元，单条最大 189.98 元 |

根因定位（不是应用代码 bug，而是**数据集未重建**）：

```bash

python3 tools/gen-perf-check.py --database smms_old   # bad=3/27   ← 修复前生成器复现同样 3 条
```

即提交 `f5090a1 fix(tools): 仿真生成器口径对齐结算服务——DEF-06~08` 修好了生成器，但**运行库与其备份 `db/backup/smms-20261009-145620.sql` 从未重新生成**（导入该备份后校验同样为 B05 474 / B06 4 / B10 844），因此 `gen-perf-check.py` 在部署环境恒 exit=1，验收门禁形同失效。

处理建议：用 HEAD 生成器按原参数重新生成数据集并替换 `db/backup/*.sql`，再跑一次 `gen-perf-check.py` 确认 exit=0。

## 3. 代码级问题

### 3.1 【中】收银结算明细含 null 元素 → NPE → 500

```bash
curl -X POST http://127.0.0.1:8802/api/v1/sales/checkout -H 'Authorization: Bearer <cashier>' \
     -H 'Content-Type: application/json' \
     -d '{"counterNo":1,"items":[null],"payments":[{"payType":"CASH","amount":9.47}]}'
# -> 200 {"code":500,"message":"系统繁忙，请稍后重试"}
```

后端日志：

```
java.lang.NullPointerException: Cannot invoke "com.smms.sale.dto.CheckoutCommand$CheckoutItem.goodsId()" because "item" is null
  at com.smms.sale.service.SalesCheckoutService.validateItems(SalesCheckoutService.java:228)
```

`@Valid` 不会校验 `List` 中的 null 元素，`validateItems` 直接解引用。期望返回 400/校验类错误码。同类入口（退货、挂单）也建议一并加空元素校验。

**已执行（2026-10-12）**：新增 `common/util/ItemRows.rejectNullRows(list, 场景名)` 守卫，覆盖 11 个请求体入口
（结算、挂单、退货、采购单增改、入库、采购退货、建议采购、供货商品、盘点范围、报损报溢单头）：命中 null 行即抛
`PARAM_INVALID(400)`，错误信息带场景名。实测 `items:[null]` 由 500 变为
`{"code":400,"message":"结算明细存在空行（items 内含 null），请检查后重新提交"}`；新增单测 `ItemRowsTest`（3 例）。

### 3.2 【低】其他健壮性观察（均已确认不会落脏数据）

`retailPrice=-1`、`changeAmount=999`、`lineType=BAD` 等客户端字段被服务端忽略（以档案价为准），结果正确；`memberId=999999` → `1511`；`payType=XXX` → `1505`；`BALANCE` 未带会员 → `1512`；`discountAmount` 非契约字段被静默忽略（契约是 `orderDiscountRate`，文档描述一致，非缺陷）。

### 3.3 【中风险】现金收款金额无上限（状态：待执行）

```bash
# 9.47 元订单，现金付款 10 亿
-d '{"counterNo":1,"items":[{...}],"payments":[{"payType":"CASH","amount":1000000000}]}'
# 落库：paid_amount=1000000000.00，change_amount=999999990.53，payment_record 记 1000000000.00
```

报表侧按 `paid_amount` 汇总实收：`mapper/rpt/ReportMapper.xml:278/316/349/439/516`、`mapper/sale/CashierShiftMapper.xml:55`、`mapper/sale/SalesOrderMapper.xml:32`。一次误输入即会把「实收/净销售额」口径放大到 10 亿。建议对单笔现金收款额设上限或二次确认。

### 3.4 【已核实为非缺陷】会员等级高于消费应享等级

初判：8 名会员 `level_id` 与 `total_consume` 应处等级不符（例：`total_consume=3505.26` 却挂 3 级）。

复核（2026-10-12，数据集重建后 300 名会员全量）：

```sql
-- 持有等级高于消费应享等级
select count(*) from member m join member_level l on l.id=m.level_id where l.threshold > m.total_consume;   -- 12
-- 持有等级低于消费应享等级
select count(*) from member m join member_level l on l.id=m.level_id
 where l.threshold <= m.total_consume
   and m.level_id < (select l2.id from member_level l2 where l2.status=1 and l2.threshold<=m.total_consume
                     order by l2.threshold desc limit 1);                                                   -- 0
```

结论：全部为「持有等级偏高」，且 0 例偏低，符合项目自身不变量 B22「会员等级 ≥ 应享等级」的口径
（等级只升不降；退货会减少 `total_consume`，但不回退已获得等级）。故**不是缺陷**，原「低频数据不一致」
表述已更正。结算路径的等级提升实测正确。
